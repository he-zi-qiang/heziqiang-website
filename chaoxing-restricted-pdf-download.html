学习通"禁止下载"的 PDF，其实门没上锁

2026 年 6 月·技术笔记·约 2,200 字

学习通/超星上很多课件标着"禁止下载"，只能在线预览。但这些 PDF、PPT 其实大多是图片预览模式——页面把文档逐页切成图片喂给你看，而完整的原文件，往往就躺在同一个目录下，公开可读。

预览图的地址形如 …/{objectid}/thumb/1.png，把结尾的 /thumb/1.png 换成 /pdf/{objectid}.pdf，就能直接拿到完整原文件。我已经验证过，确实奏效。

仅用于下载自己有权访问的课程资料、自用学习。下面更想聊的，其实是这个技巧为什么成立。

核心原理：预览图和原件是同一窝的兄弟文件

预览页里那一张张图片，和完整 PDF 放在同一个对象目录下。服务端把上传的 Word/PDF 切成 thumb/1.png、2.png… 做预览，但完整 PDF（pdf/{objectid}.pdf）作为转码副产物通常照样存着，而且没单独做访问控制，直接能取。

两者的地址只差最后一段：预览图是 …/doc/b2/38/19/{objectid}/thumb/1.png，完整 PDF 是 …/doc/b2/38/19/{objectid}/pdf/{objectid}.pdf。其中 {objectid} 是 URL 里那段 32 位十六进制，预览图和 PDF 用的是同一个。

操作流程

打开 PDF 预览页面（带 iframe 那个），按 F12 打开开发者工具的 Network（网络）面板，刷新页面让 PDF 重新加载。在过滤框里输入 thumb 或 1.png，就能找到预览图链接。复制它，把 /thumb/1.png 替换成 /pdf/{objectid}.pdf，在新标签页打开替换后的链接，右键"另存为"即可。

如果链接打不开，有三个兜底可以挨个试：把域名 s3.cldisk.com 换成 s3.ananas.chaoxing.com；把 https 换成 http；objectid 取不到时，去页面源码或 URL 里翻那段 32 位十六进制。

这不是破解，是绕过形同虚设的权限

得先把性质说清楚：所谓"禁止下载"，没对文件本身做任何加密或鉴权，只是前端把下载按钮藏起来、用图片代替原文件展示。原件一直躺在公网可访问的地址上——你做的不是解密，是直接敲那扇本就没上锁的门。

「预览图能加载，本身就证明这个桶是公开可读的。预览功能亲手泄露了'这里没上锁'。」

为什么地址能猜得出来？因为 s3.cldisk.com / s3.ananas.chaoxing.com 是超星的对象存储 / CDN。对象存储本质上是"扁平的 key → 文件映射"，URL 路径就是 key。路径里 doc/b2/38/19 是按哈希前缀打散海量文件的分桶目录（注意它并不等于 objectid 的前缀，是另算的一层哈希）；{objectid} 是文档唯一 id，前端渲染预览时必然暴露在页面里；thumb/ 和 pdf/ 则是同一文档不同衍生物的命名约定。

拿到 objectid，再知道这套命名约定，就能拼出原件的 key。整条路径是可预测、可枚举的。

它的学名：Broken Access Control / IDOR

放到安全的语境里，这正是 OWASP Top 10 排第一名（A01）的 Broken Access Control（失效的访问控制）。病根在于：权限校验做在了 UI 层（藏按钮），而没做在资源层（文件本身）。配合它的是 IDOR（不安全的直接对象引用）——靠构造或猜测对象地址，拿到本不该给你的资源。

那三个兜底各有各的道理：换域名有效，是因为同一对象常挂在多个 CDN/域名后面（容灾、历史迁移），换域名等于换个入口绕过某条线路的限制；把 https 换成 http 有效，是因为没强制 HTTPS 跳转、没上 HSTS 时，http 入口也能取到同一资源；去源码里找 objectid 有效，是因为前端要渲染预览，就必然把它写进 DOM、JS 或请求里，藏不住。

泛化：任何"只让看不让下"的系统

「预览 ≠ 没有原件。去 Network 看它到底加载了什么，原件常在某个可猜的兄弟路径上。」

这套心法可以套到很多场景。通用四步是：抓包看真实资源 URL → 找命名规律 → 改路径试原件 → 换域名/协议/去缩略参数重试。

比如 OSS 图片常带 ?x-oss-process=image/resize,… 的缩略处理参数，删掉问号后面的部分就能拿原图；命名式缩略图（xxx_thumb.jpg、_small）去掉后缀即可；视频是 m3u8 加 ts 切片，可以找同目录的 mp4，或用 ffmpeg 合并 ts；付费音频、字体则去 Network 里翻真实的 .mp3 / .woff 地址。

什么时候会失效——也就是正确的防护长什么样

反过来看，遇到下面这些情况基本就拼不出来了，它们恰好是判断一个系统"防得对不对"的标尺。

最关键的是预签名 URL：地址带上 ?Expires=…&Signature=… 这类参数（S3 是 X-Amz-Signature），签名只对特定 key、有限时间有效，你一改路径就失配，直接 403。其次是私有桶加服务端鉴权代理，请求走 /api/file?id=… 带 Cookie/Token，后端每次校验身份与权限。再有 Referer 防盗链、Token 校验，直链打开就被拒。以及预览图本身就是动态鉴权接口、而非静态对象，那就没有可猜的静态原件路径。

「学习通栽在'该用签名 URL 的地方用了公开直链'。这招能存活，等于他们这道题没做对。」
我把这套流程开源并做成了一个小工具 chaoxing-pdf-dl：默认走无登录直链，也支持带 cookie 解锁只给 objectid 或整课批量，能从页面 HTML 提取、读剪贴板、还原真实文件名。同类"把预览图地址改成原文件地址"的思路，对其他切片式预览的网盘、文库也常常奏效。
